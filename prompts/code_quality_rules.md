## Code quality: write like a long-time maintainer, not like a model
Reviewers reject contributions that *smell* machine-generated even when they are correct. The diff must be indistinguishable from a careful human contributor who has read the surrounding code. Concretely:
- **Match the file, not a style guide.** Measure the surrounding code before writing: comment density, docstring presence/format on private helpers, type-hint usage, assert-message habits in tests, naming, line length, error-handling idioms. Mirror it exactly, even where you'd personally do otherwise.
- **No narrating comments.** Never comment what the code visibly does ("# loop over items", "# check if empty", "# return the result", "This function ..."). Comment only *why*, and only where a reader would otherwise be puzzled. Typical good diffs add 0–2 comments.
- **No docstrings or comments on new private helpers.** A short helper's name and body are its documentation. Never write a docstring that restates the function name or paraphrases a sibling's docstring. Public API additions may carry a docstring only in the exact format the file already uses; no `Args:/Returns:` sections unless the file has them.
- **No defensive re-validation.** Don't re-check types/None/ranges that callers or the surrounding code already guarantee; don't wrap things in `try/except Exception`; don't add `isinstance` guards "just in case"; don't validate the same thing an existing helper validates: reuse that helper.
- **No copy-paste.** If you need behaviour that exists nearby, call or extend it; never duplicate a block.
- **No filler vocabulary** in code, comments, commit messages or PR text: robust, comprehensive, seamless, leverage, enhanced, gracefully, ensure(s) that, in order to, "it's worth noting", "best practice", "for clarity". No em/en dashes (— –). No emoji. No markdown headings/bold in commit messages.
- **No scope inflation.** No unrelated refactors, renames, reformatting of untouched lines, added type hints to untouched signatures, reordered imports, "while I was here" fixes.
- **Tests read like the repo's tests.** Same fixtures/mocking style, same assertion style, same naming length. One clear failing-before/passing-after test beats six redundant assertions. Don't add assertion messages if the repo's tests mostly don't.
- **Commit messages and PR text** are terse, factual, first-person-plural-free ("Fix X when Y" / "Add Z"), follow the repo's `git log` conventions, and never mention that AI wrote anything unless the repo's policy requires disclosure (then follow that policy exactly).
- **Naming** follows what neighbours do; no `_helper`, `_utils`, `handle_*`, `process_*`, `do_*` unless the file already uses that pattern.
- **Written repo conventions override every heuristic above.** If AGENTS.md / CONTRIBUTING / a style doc mandates something (e.g. "add terse descriptive strings to asserts"), do exactly that, in the repo's own voice, even if it looks like a pattern listed here.
Before you finish, re-read your diff as a skeptical maintainer and delete anything that fits the list above.
